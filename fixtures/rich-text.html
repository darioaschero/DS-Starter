Rich text

data-ui="rich-text" maps semantic prose HTML to typography roles inside @scope (…) to (:scope [data-ui]). The root carries no rule at all, so the component adds nothing inheritable of its own. Note that code on this page, outside any rich-text article, renders with plain UA styling — the scoped rules do not exist out here.

Mixing strong and code() in a heading

Inline semantics never carry a full font role, so the strong above keeps the heading's size and line height, and the inline code shrinks relative to the heading via its intentional 0.9em.

The containment rule itself, as a code block:

@scope ([data-ui="rich-text"]) to (:scope [data-ui]) {
  :where(h2) { font: var(--ds-rich-text-h2-font, var(--ds-type-heading-md)); }
  :where(p, li, dd, dt, blockquote, td, th) { font: var(--ds-rich-text-body-font, var(--ds-type-body-md)); }
  /* a deliberately long line to demonstrate that overflowing code scrolls inside the block instead of widening the article */
}

What crosses the rich-text boundary

Crosses into the article by ordinary inheritance from the page (this fixture's chrome rule on body): color var(--ds-text-primary); font family, size and weight from var(--ds-type-body-md); line-height 1.5. Unmapped elements inside the article — the nested probe's contents — show exactly these inherited values plus UA element defaults.

Contributed by the rich-text root itself: nothing. The component has no root rule, so nothing inheritable originates at the boundary; every declaration sits on prose elements inside the scope. Evidence: the two probes above compute identically (font-size, font-weight, line-height, color, margin-block-start).

Public --ds-rich-text-* properties inherit like any custom property — including into nested components — but are inert there: only scoped rules read them, and scoped selectors stop at nested [data-ui] boundaries.
